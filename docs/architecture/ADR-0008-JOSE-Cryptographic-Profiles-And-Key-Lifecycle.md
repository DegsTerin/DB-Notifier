# ADR-0008 — JOSE Cryptographic Profiles and Key Lifecycle

- Status: proposed
- Date: 2026-07-28
- Owners: security, identity and platform architecture
- Decision authority: a separate architecture and security review is required

## Context

The Server API already validates externally issued signed JWT bearer tokens
through OIDC discovery and JWKS retrieval. That implementation proves a
bounded JWS/JWK consumption path, but it is not a complete JOSE capability:
there is no JWE processing, no general or flattened JSON serialisation, no
product-owned key lifecycle, no purpose-specific algorithm registry, and no
operational IdP, vault, KMS or HSM.

DB-Notifier may need JOSE for human identity tokens, signed control artefacts,
confidential envelopes and future multi-signature evidence. Those purposes
have different issuers, audiences, keys, replay rules and trust decisions.
Treating all JOSE objects as interchangeable would permit algorithm
confusion, cross-token substitution and inappropriate key reuse.

“Complete JOSE” therefore means complete, testable coverage of the applicable
JOSE processing models and serialisations under explicit profiles. It does
not mean enabling every algorithm in the IANA registry. Algorithms that are
deprecated, prohibited, unsuitable for the deployment or unsupported by an
approved key custodian remain explicitly rejected.

## Proposed decision

If this ADR is accepted, DB-Notifier will introduce a versioned JOSE
capability governed by immutable, purpose-specific cryptographic profiles.
Each profile will bind:

- operation: sign, verify, encrypt or decrypt;
- artefact type and explicit `typ`/`cty`;
- issuer, subject and exact audience rules where claims apply;
- accepted serialisation and nesting order;
- exact algorithm and key-type allowlists;
- trusted key source and permitted key identifiers;
- maximum encoded, decoded, header, recipient, signature and nesting sizes;
- time, replay, rotation and revocation rules;
- stable sanitised failure codes; and
- an owning policy version and audit purpose.

The recipient never selects policy from an untrusted `alg`, `enc`, `typ`,
`cty`, `kid`, `jku`, `jwk`, `x5u` or `x5c` value. It selects a trusted
purpose profile first and then verifies that the object is an exact subset of
that profile.

## Standards boundary

The normative baseline will cover:

- RFC 7515: JWS Compact, Flattened JSON and General JSON serialisations,
  including detached content;
- RFC 7516: JWE Compact, Flattened JSON and General JSON serialisations,
  including authenticated additional data and multiple recipients;
- RFC 7517: JWK and JWKS representation;
- RFC 7518 plus the live IANA JOSE registries: JWA identifiers and key
  parameters;
- RFC 7519: JWT claims and nested signed/encrypted JWTs;
- RFC 7638: JWK thumbprints;
- RFC 7797: unencoded JWS payloads, disabled unless a purpose-specific profile
  explicitly requires and tests them;
- RFC 8725: JWT security best current practices; and
- RFC 9864: fully specified algorithm identifiers and the current meanings of
  deprecated and prohibited registry states.

Related formats such as COSE, SD-JWT, JSON Web Proof, DPoP and application
protocols that merely use JOSE are not silently included. Each requires its
own use case, threat model and compatibility decision.

## Initial algorithm policy

The final allowlist remains subject to platform, IdP and key-custodian
homologation. The proposed starting policy is:

| Class | Proposed posture |
|---|---|
| JWS production preference | `PS256` or `ES256`, selected per purpose and key-custodian support |
| JWS inbound compatibility | `RS256` only for an explicitly configured external issuer during a documented migration or compatibility period |
| Modern Edwards signatures | evaluate the fully specified `Ed25519` identifier from RFC 9864; do not enable until the complete .NET, IdP, KMS/HSM and cross-platform path is proved |
| Symmetric JWS | deny across independent trust boundaries; any future same-owner MAC profile requires a separate decision and distinct key |
| Unsecured JWS | always deny `alg=none` |
| JWE content encryption | prefer `A256GCM`; every nonce is generated by an approved CSPRNG and never reused with the same key |
| JWE key management | start with `RSA-OAEP-256`; evaluate ECDH-ES with an exact curve/key policy before use |
| Legacy JWE | deny `RSA1_5`, CBC-based content encryption and password-based key management in the baseline |
| Compression | deny `zip` by default to avoid compression side channels and decompression amplification |

Every entry in the IANA JOSE algorithm, header and key-type registries must be
classified as `Adopted`, `Safely adapted`, `Rejected` or `Scheduled`, with
reason, allowed purpose, library support, custodian support, tests and review
date. Registry presence alone never grants runtime support.

## Architecture placement

- Domain remains independent of JOSE, cryptography, identity providers and
  key stores.
- Application owns immutable purpose, policy, outcome and port contracts. It
  does not parse keys or invoke cryptographic primitives.
- A dedicated infrastructure boundary owns JOSE parsing, serialisation and
  approved-library adapters. It may become a separate
  `DBNotifier.Infrastructure.Security.Jose` assembly only if dependency and
  ownership analysis proves that the existing Infrastructure assembly would
  otherwise couple unrelated runtimes.
- Server API composition selects human identity, control artefact and
  confidentiality profiles explicitly. It does not become a password
  database or a general-purpose token issuer.
- Agent identity remains mTLS. JOSE does not replace certificate
  authentication, route binding, revocation or the durable Agent protocol.
- Dashboard uses a separately approved OIDC browser flow. It never receives
  private signing/decryption keys or makes authorisation decisions.
- Providers and monitored databases remain outside JOSE policy and never
  receive human tokens, key material or decrypted control envelopes.

No hand-written cryptographic primitive will be introduced. Approved .NET
libraries provide primitives and constant-time validation where applicable;
DB-Notifier owns profile enforcement, bounded parsing, trust selection,
auditing and integration.

## Key and trust lifecycle

Signing, verification, encryption and decryption keys are separate by
environment, tenant where applicable, purpose and direction. Private or
symmetric material:

- resides in an approved OS vault, corporate vault, KMS or HSM;
- is addressed only by an opaque versioned reference;
- is non-exportable where the platform permits;
- never appears in configuration, PostgreSQL, SQLite, logs, exceptions,
  telemetry, screenshots, reports, tests or chat output; and
- is never backed up by pretending that a DB-Notifier metadata backup
  contains the external key.

Rotation uses a staged sequence: publish or admit the new public key, activate
new production, retain the old verification/decryption key for the bounded
overlap, stop new use of the old key, drain the maximum artefact lifetime,
retire it, and prove refusal after retirement. Compromise recovery is a
separate audited ceremony with revocation, cache invalidation, quarantine and
reissuance; it is not ordinary rotation.

Public JWKS endpoints, when a DB-Notifier use case genuinely requires one,
publish public material only, use HTTPS, strong cache semantics and ETags,
bound document size/cardinality, and never reveal tenant topology or private
metadata. Remote key acquisition is limited to preconfigured trusted issuers
through the existing network-egress policy. Token-provided `jku` or `x5u`
values never create network authority.

## Processing rules

- Reject duplicate JSON member names, malformed or padded base64url,
  excessive depth/cardinality and unknown critical headers before expensive
  cryptographic work.
- Require protected `alg`; require protected `enc` for JWE. Security-relevant
  routing values cannot reside only in an unprotected header.
- Enforce exact key type, key use, key operations, curve, size and algorithm
  binding. A matching `kid` is a lookup hint, not proof.
- Validate every signature required by the selected multi-signature policy;
  never accept an arbitrary favourable signature.
- Validate the JWE authentication tag before releasing plaintext and expose
  one indistinguishable decryption refusal to callers.
- For confidential JWTs, use sign-then-encrypt and require the inner JWS and
  outer JWE to satisfy different, explicit profiles. Encryption never
  substitutes for issuer authentication.
- Apply mutually exclusive validation rules for access tokens, ID tokens,
  control artefacts and any other JWT type.
- Bound `exp`, `nbf`, `iat`, `jti`, issuer, subject, audience and clock skew
  per purpose. Replay storage is introduced only where the use case requires
  single use or idempotency and remains separate from token validation.
- Never log or persist a raw token, plaintext, ciphertext, authentication tag,
  private JWK, symmetric key or unrestricted claim set.

## Data and infrastructure consequences

Ordinary persistence may store only non-secret metadata such as purpose,
policy version, opaque key reference, public-key thumbprint, lifecycle state,
activation/retirement times and audit correlation. Any new schema requires a
separate data-model decision and non-production migration.

Production infrastructure requires independently selected and homologated:

- external IdP and OIDC browser/API configuration;
- vault/KMS/HSM adapters and workload identity;
- trust bootstrap and public-key distribution;
- rotation, revocation and compromise-recovery runbooks;
- high-availability and cache behaviour during custodian or IdP outage;
- environment-specific policy deployment without secrets in packages;
- observability, alerting and audit retention; and
- backup/restore that reconciles metadata with external key state.

An unavailable or stale trust/key dependency fails closed for new protected
operations. A bounded last-known-good public verification set may remain
usable only under an explicit freshness policy; private-key unavailability
never falls back to a local plaintext key.

## Alternatives

### Continue with JWT bearer validation only

Rejected as the target decision because it does not meet the requested JWE,
general JSON serialisation, multi-recipient, key lifecycle or reusable signed
artefact requirements. It remains the safe current baseline until later lots
are authorised and pass their gates.

### Enable every algorithm supported by a library

Rejected. Library capability is not a security policy, and it changes with
dependency versions. This option increases downgrade, confusion and legacy
algorithm exposure.

### Build a custom JOSE implementation

Rejected. Custom cryptographic primitives and ad hoc parsers would create an
unacceptable assurance and maintenance burden.

### Use JOSE for all internal messages

Rejected. HTTPS/mTLS, durable signatures, idempotency and database controls
already have distinct responsibilities. JOSE is introduced only where its
object-level properties are required and must not duplicate or weaken those
boundaries.

## Acceptance conditions

This ADR may move from `proposed` to `accepted` only when:

- security, identity, platform and data owners approve the use-case and trust
  maps;
- the standards and IANA coverage matrix has no unclassified entry;
- library and platform spikes prove required serialisations without custom
  cryptography;
- the algorithm profile is compatible with the chosen IdP and key custodian;
- threat-model, migration, rollback and outage behaviour are complete;
- secret handling and audit fields have been reviewed; and
- the Human Gate records the reviewed evidence and reservations.

Acceptance of this ADR would constrain future implementation. It would not
authorise code, dependencies, migrations, external services, keys, deployment
or lifecycle progression.
